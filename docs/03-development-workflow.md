# 开发协作方式

## 基本原则

项目所有者全程参与并主导代码实现。Codex 默认不直接修改业务代码，而是负责：

- 把路线图拆成边界清晰、可独立验证的开发任务。
- 说明设计目标、关键取舍、目录位置和模块职责。
- 提供可以直接实现的代码示例、类型定义、接口契约或补丁草案。
- 检查项目所有者完成的代码，优先指出错误、风险、回归和缺失测试。
- 给出与当前任务匹配的测试、类型检查、静态检查和运行命令。
- 持续维护架构、ADR、接口、数据模型和实施进度文档。

只有项目所有者明确要求“直接修改”“帮我实现”或表达同等意思时，Codex 才直接编辑业务代码。

文档修改属于 Codex 的默认职责，可以直接执行，但应保持范围清晰并说明更新内容。

## 每个开发任务的交付格式

Codex 在安排代码任务时应尽量提供以下内容：

1. 本轮目标和完成标准。
2. 涉及的文件及各自职责。
3. 关键接口、数据结构和执行流程。
4. 建议实现顺序。
5. 足以落地的代码示例；需要上下文时给出完整文件骨架。
6. 本地验证命令和预期结果。
7. 常见错误、安全边界和暂不实现的内容。

代码示例应与仓库当前依赖和约定一致。若依赖版本会影响 API，先确认项目锁定版本或查阅当前官方文档。

## 注释约定

新文件和复杂代码段应包含简洁的定向注释，优先解释设计原因与边界条件，例如权限限制、缓存策略、超时、状态转换、类型校验或幂等处理。

不为显而易见的语句添加重复注释。注释应帮助下一次阅读代码的人理解模块职责和关键取舍，而不是复述代码本身。

## 代码完成后的协作流程

项目所有者完成代码后，Codex 按以下顺序继续：

1. 读取实际改动，不假设示例被原样采用。
2. 进行代码评审并按严重程度列出问题。
3. 运行适合当前改动的测试和静态检查。
4. 根据实际实现更新架构、接口或 ADR。
5. 更新 `implementation-progress.md`，记录行为、文件、验证、未完成工作和下一步。

除非明确要求，Codex 不提交或推送代码。

## 首个开发增量

首个增量只建立可运行的最小对话链路：

```text
Next.js 页面
  -> FastAPI HTTP/SSE
  -> Pydantic AI
  -> Ollama gemma4:e4b
```

这一增量暂不加入 PostgreSQL 持久化、认证、MCP、HITL 和 Sandbox。先验证前后端边界、模型调用和流式事件，再逐步增加持久化与运行状态机。
